# Rule: Ship, don't perfect

In a hackathon context:

- Prioritize working software over elegant code.
- Suggest the simplest implementation that demonstrates the idea.
- Flag technical debt inline with `// TODO:` comments rather than stopping to fix it.
- If the student asks "should I refactor X?", the answer during a hackathon is almost always "after the demo".
- Focus on the demo path: what will the judges see, and does that work end-to-end?
